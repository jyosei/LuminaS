# 技术栈与选型决策

日期：2026-10-12。这是本项目的工程建议；性能与质量必须由 P0 证明。依赖的具体版本在 P0 按兼容组合固定进 Cargo.lock 和原生依赖清单，不分别追逐最新版本。

## 主方案

| 层 | 选择 | 理由与限制 |
|---|---|---|
| 业务与图像核心 | Rust stable，Cargo workspace | 便于模块化、并发与内存所有权管理；FFI、驱动与算法质量仍需独立验证 |
| 桌面界面 | egui + eframe，wgpu 后端 | 原生编译的自绘界面；适合快速迭代编辑工具和共享 GPU。不是系统原生控件；中文 IME、无障碍、拖放与高 DPI 是 P0 门槛 [S1] |
| 渲染/计算 | wgpu + WGSL | Windows DX12 优先，Vulkan 为可测备选；后续 macOS Metal / Linux Vulkan。GPU 支持取决于实际驱动、格式和特性，不能承诺所有设备通用 [S2] |
| CPU 图像处理 | 自有算子 + Rayon | 同一数学定义的 CPU 参考实现与兼容路径；先实现已交付功能对应的算子，不引入整个 OpenCV 做默认依赖 [S10] |
| RAW 读取 | LibRaw，通过小型 C ABI 包装 | 成熟读取能力；保持 RAW 元数据和线性输出。双许可，选择 LGPL-2.1 路径动态链接并按实际发布包审查；不用额外 GPL demosaic packs [S3] |
| 色彩管理 | Little CMS 2，小型 FFI 包装 | 输入/显示/输出 ICC 变换；GPU 显示 LUT 需与 CPU 结果校验 [S4] |
| 常规编解码 | Rust image 生态先跑通；必要时局部接 libjpeg-turbo / libtiff | 首轮仅开需要的格式特性；TIFF 的 16-bit、ICC、EXIF、压缩变体必须逐项确认，不假设一个通用接口自动支持全部元数据 |
| 项目与设置 | rusqlite + SQLite；serde / serde_json | 文档元数据、事务和块内容；原图按块存储，持久化与可重建缓存分开 [S11] |
| 日志/错误 | tracing + thiserror | 限额本地日志，任务上下文和用户可理解的错误；日志不写图像内容或密钥 |
| AI 选区/降噪 | 独立 ai-worker，ONNX Runtime C API 适配层 | CPU 基线先验证；Windows GPU 评估 Windows ML；AI 包独立下载。Rust 绑定库是替代选项，维护和 ABI 要评估 [S5] |
| 生成式 AI | 提供商协议，首选用户本地 HTTP 服务 | 接已有生成工作流；不把完整 Python 环境塞进基础安装包，不绑定唯一模型 |
| 构建/分发 | Cargo + 原生库 CMake；Windows portable ZIP 起步 | 单一仓库、锁定工具链和原生库构建选项；正式安装器、签名和自动更新之后再加 |

资料索引见 [技术来源](05-sources.md)。

egui 是默认选型，不等于它已经证明能完成精致摄影 UI。先开发带中文输入、滑杆、颜色控件、图层列表、触控板与数位笔的验证窗口；确认 UI 体验与按需重绘。若核心 UX 无法达到门槛，保留 Rust 核心，桌面层转为 Qt 6 Widgets + C++，使用窄 C ABI 共享核心。

CPU 图像计算回退不等于无 GPU 的整个窗口可运行：eframe/wgpu 自身仍需要可用渲染后端。P0 必须测试弱 GPU 和驱动丢失；完全软件 UI 渲染不作为首版承诺。不满足桌面渲染条件时提供清晰错误，核心仍可用于后续命令行导出。

## 为什么这样选

| 候选 | 优点 | 主要成本 | 结论 |
|---|---|---|---|
| Rust + egui + wgpu | 统一核心与 GPU；自绘界面不需要浏览器壳；适合限额缓存设计 | 摄影交互、原生体验和无障碍要自己打磨 | 默认方案，先通过 P0 |
| C++ + Qt 6 Widgets | 成熟桌面控件、复杂交互经验多；足以做轻量程序 | C++ 核心维护；GPU 跨平台路径与模块许可要管理 | 如果已有强 C++/Qt 经验，可能比主方案更快交付；保留作 UI 备选 [S8] |
| Tauri + Web UI + Rust | Web UI 开发效率好，可用系统 WebView | 画布/核心跨边界调度、纹理传输、ICC 与高频笔刷路径要验证 | 合理方案，但当前不作为摄影画布首选；不能因安装包小断言运行内存低 [S9] |

轻量化主要来自算法与数据流，不存在“Rust 自动省内存”或“Qt 必定臃肿”的结论。若团队熟悉另一条路线，应按同一场景实测后重选。

## AI 技术选择的实际边界

MobileSAM 作为低开销点/框选区的首个候选，SAM 2 tiny 作为质量对照。仓库宣称 MobileSAM 支持 ONNX 导出，但官方脚本输入是 image_embeddings，实际导出的是提示编码与 mask 解码。完整部署必须单独导出图像编码器，校验 resize、padding、归一化与坐标映射，并对 CPU/GPU 结果做一致性检查。不要直接把论文设备上的时延当成本机承诺 [S6, S7]。

生成式服务用专用适配器描述能力：是否接受 mask、输出尺寸、最大裁片、取消语义与模型版本。可以先接 ComfyUI 类本地服务，但具体 API 适配在实现时根据其官方资料核实，不假设“OpenAI-compatible”代表所有服务都有局部改图能力。

ONNX Runtime 官方已将 DirectML 标为持续维护模式，新的 Windows 路线优先 Windows ML。因此主架构面向 ONNX 语义而非绑死 DirectML。P0 比较独立 ORT CPU 与 Windows ML 的部署、Rust/C ABI 和离线可用性；旧系统的 DirectML 兼容适配是可选项。模型算子、量化类型和 GPU 执行提供商分别验证 [S5]。

## 开源方案

推荐项目代码 Apache-2.0：便于贡献、复用和明确专利授权；它允许闭源衍生，这是需要接受的取舍。若首要目标是衍生版本持续开放，可选择 GPL-3.0，但须重新审查所有依赖和分发组合。这些是项目治理选择，不是法律结论。

发布时分别记录应用源码、FFI 库、第三方代码、字体、模型权重、测试照片和训练来源。仓库的代码许可证不能自动证明每个模型文件可再分发。LibRaw 动态链接不是履行 LGPL 的全部要求；需要包含许可证、对应源码/修改与用户替换库的安排，并检查实际构建和分发义务。AI 包有单独 manifest、来源、哈希与许可文本。

建议从第一批代码开始有 CONTRIBUTING、架构决策记录、版本化项目格式、缺陷模板、Windows CI；引入依赖时记录构建特性，避免把未用到的库和模型装进去。

## 建议优先统一的设计原则与待定实现

建议优先统一：非破坏模型、命令接口、颜色契约、坐标语义、资源预算和任务版本号。它们尚未实现；具体分块策略、进程隔离时机和接口设计可由审查调整，不视为用户已经批准。

暂缓到验证后：egui 具体兼容版本组、512 或 256 tile、工作色域的最终默认值、降噪参数标定、完整 AI 模型、安装器、正式项目许可证。默认建议不等于已经通过测试。

完整审查问题见 [交接决策表](../handoff/DECISIONS.md)，特别需要重新检查精细 UI 的框架成本、RAW 显影自研范围、P0 的 AI 门槛和 SQLite/多进程的初期复杂度。
